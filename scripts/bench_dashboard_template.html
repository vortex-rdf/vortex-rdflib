vortex-rdflib · bench SPARQL over rdflib stores — comparative benchmark
Overview Load Queries Memory Query set Raw data

One run of bench/run_bench.py: vortex-rdflib's VortexRdflibStore against rdflib, oxrdflib (Oxigraph), pycottas-rdflib (COTTAS) and rdflib-hdt (HDT), over a synthetic SPARQL set: lookups and scans, star and chain joins, FILTER / DISTINCT / ORDER BY / GROUP BY, and patterns that name a graph. The Vortex rows are all Dictionary layout, crossed over residency and secondary index (none, by-copy, by-reference).

rdflib's engine evaluates every store but the last, so the store serving quad patterns is the only variable among the rows that are ranked against each other. The exception is oxrdflib (pyoxigraph engine): the same Oxigraph store answering through pyoxigraph's own SPARQL engine instead, ruled off as the reference point the rdflib rows are working against. Each label records where a query's bytes come from: in-mem stores live fully in memory, file stores perform file access reads per query. Every query matches by construction, and row counts are cross-checked across stores.

The dataset is composed of quads: every statement about a subject goes into one graph, so the union of the graphs forms a triple set that queries that name no graph see. Each store loads it as an rdflib Dataset whose default graph is that union. HDT and COTTAS cannot serve named graphs through rdflib — HDT's format has none, and pycottas' store does not expose the ones COTTAS files can hold — so those two rows load the flattened N-Triples and do not report measurements in the Named graphs panel.

LOAD

Source file to queryable store

Cold start: from the shared source file — .nq for the stores with named graphs, the flattened .nt for HDT and COTTAS — to a queryable store. The same statements either way, but not the same bytes: dropping the graph column makes the .nt about 18% smaller, so those two rows have that much less to parse. Most libraries build their own format first — serialize_rdf (vortex-rdflib), rdf2cottas, hdt convert — then open it; rdflib and oxrdflib parse directly. Median of repeated full rebuilds. rdflib-hdt is read-only: it cannot write HDT, so its file is built by the Rust hdt crate's CLI and only opened by the library measured here — that row's build is another implementation's work, unlike every other row.

QUERY

SPARQL execution, per query

Median wall-clock time to execute and fully consume each query, reported as a pair of figures taken from one run, split where rdflib's own string path splits: exec only is the evaluation of an already-translated algebra — the part a store's speed can move; full adds the parse and algebra translation in front of it, which rdflib repeats on every string query. full is what an application passing a query string waits for, and on a selective query it is nearly all of it — no store can be faster than rdflib's parser. Green marks the fastest cell in each column outright, whichever engine produced it, and the grey multiplier is every other cell's slowdown against it. In the full columns that is usually the ruled-off pyoxigraph-engine row; the exec only column beside it is where the same question is answered among the stores rdflib evaluates, since that row has no cell there.

Two marks on the column headers. • is a heavy query — it touches the whole dataset, and runs on a lower iteration budget. ‡ is a query whose answer is a cardinality, not rows: a ground ASK, or an ungrouped COUNT(*) over one pattern. A store that can count a selection without materializing it answers those without decoding a single term, so those columns compare an approach — whether the store can answer from counts at all — and not how fast one implementation walks rows. The ratios there are real, and they do not generalize to the other columns.

The last row, oxrdflib (pyoxigraph engine), is ruled off because it is a different engine rather than a different store: the same Oxigraph store asked without use_store_provided=False, so pyoxigraph parses the SPARQL, plans the joins and returns the rows, and rdflib evaluates nothing. Read it as the reference point every rdflib row is working against, rather than a like-for-like row — it takes the green marker on most full columns because it is genuinely fastest there, not because it is doing the same work. It is not a measurement of pyoxigraph: every solution still crosses into Python through oxrdflib one value at a time, to produce the rdflib terms every other row produces, and for a query that returns rows that conversion — not the engine — is most of the number. Against the raw pyoxigraph.Store it stands in for, this row runs roughly an order of magnitude slower on the row-returning queries. Its exec only cells are empty because rdflib's prepared algebra cannot cross that boundary — OxigraphStore.query rejects a parsed query and rdflib silently falls back to its own evaluator, so a figure taken that way would be rdflib's engine under this row's name. Its full figure is the honest comparison: every full cell answers "here is a query string, here are the rows".

rdflib-hdt's own optimize_sparql() fast path is switched off: it answers two of these joins wrongly — chain-2 with 26 rows and optional with 152, against the 18 and 1 that rdflib and rdflib-hdt itself return without it. That row therefore runs on rdflib's engine, as every other row does.

MEMORY

Peak memory (RSS)

Each store's whole lifecycle runs in its own process — build, every query, result materialization — so this is a clean per-store peak resident-set size: the kernel high-water mark (VmHWM), not a sample. Lower is better.

SET

The query set

Anchor terms and thresholds come from the dataset generator's modular arithmetic, so every query matches at least one row. heavy queries touch the whole dataset and run with a lower iteration budget.
