A run of bench/run_bench.py: vortex-rdflib's VortexRdflibStore against itself and:

  • rdflib (default)
  • oxrdflib (rdflib over an Oxigraph store)
  • pycottas-rdflib (rdflib over a COTTAS store)
  • rdflib-hdt (rdflib over an HDT store)
  • pyoxigraph (Oxigraph's own Python bindings)

Using a synthetic SPARQL set that includes lookups and scans, star and chain joins, FILTER / DISTINCT / ORDER BY / GROUP BY, and patterns over named graphs. The Vortex configurations use all a Dictionary layout, varying its residency (in-memory or file-backed) and secondary index (none, by-copy, by-reference).

rdflib's engine evaluates every store (except for pyoxigraph), to isolate the impact of every store overquad patterns reads. pyoxigraph is Oxigraph's own Python bindings used directly (its own parser, engine and terms, with no rdflib dependency). The labels specify where data comes from: in-mem stores live fully in memory, file stores perform file access reads per query.

The test dataset is composed of quads. Every statement about a subject goes into one graph, so the union of the graphs forms a triple set over which queries that name no graph operate. Each store loads it as an rdflib Dataset whose default graph is that union. pyoxigraph loads into its own store, queried with that union as its default graph. HDT and COTTAS cannot serve named graphs through rdflib — HDT's format has none, and pycottas' store does not expose the proper store interface for it. These stores use flattened N-Triples and do not report measurements in the Named graphs panel.

The BSBM tab of every section runs the same stores on the Berlin SPARQL Benchmark's Explore use case: data from the official generator, and the query streams the unmodified official test driver sends, captured once. Each store answers the warm-up mixes, then every measured query instance once, with the parameters the driver drew for it. A query over the per-query timeout is aborted and counted; a store over its time budget finishes its mix and stops, marked partial.

LOAD

Source file to queryable store

Cold start: from the shared source file — .nq for the stores with named graphs, the flattened .nt for HDT and COTTAS — to a queryable store. The same statements, but not the same bytes: dropping the graph column makes the .nt about 18% smaller, so those two libraries have that much less to parse. Most libraries build their own format first — serialize_rdf (vortex-rdflib), rdf2cottas, hdt convert — then open it; rdflib and oxrdflib parse directly, and pyoxigraph bulk-loads the file with its own parser. Median of repeated full rebuilds. rdflib-hdt is read-only: it cannot write HDT, so its file is built by the Rust hdt crate's CLI and only opened by the library measured here.

From the official generator's dataset.nt to a queryable store, with each store's own build step as on the synthetic tab. BSBM has no named graphs, so every store reads the same file. One build per store at this scale.

QUERY

SPARQL execution, per query

Median wall-clock time to execute and fully consume each query, reported as a pair of figures taken from one run: exec only is the evaluation of an already-translated algebra — the part a store's speed can move; full adds rdflib's parse and algebra translation. Green marks the fastest cell in each column, and the grey multiplier is every other cell's slowdown against it.

Two marks on the column headers. • is a heavy query — it touches the whole dataset. ‡ is a query whose answer is a cardinality (e.g., ASK or COUNT(*)).

rdflib-hdt's own optimize_sparql() fast path is switched off: it answers two of the queries wrongly — chain-2 with 26 results and optional with 152, against the 18 and 1 that rdflib and rdflib-hdt itself return without it. That row therefore runs on rdflib's engine, as every other row does.

The BSBM Explore mix — 25 queries over eleven templates (Q1–Q12 without Q6, Q5 twice) — run as the official driver runs it: warm-up mixes first, untimed, then every measured instance once with its own parameters. A cell is the template's mean over its instances (BSBM's AQET; hover for the median), exec only and full as on the synthetic tab. Answers are checked instance by instance: the rdflib-engine stores' answer digests must agree and pyoxigraph's row counts must match theirs; a disagreement is listed with the overview's failures.

MEMORY

Peak memory

Each store's whole lifecycle runs in its own process: build, every query, result materialization. Peak RSS is the kernel high-water mark (VmHWM), which counts file pages a store maps and the kernel may drop again; Peak anon is the highest anonymous memory (RssAnon) sampled after the build and after every query: the memory the process itself holds. Lower is better.

The same two figures over the BSBM run: build, warm-up and measured mixes, with RssAnon sampled after the build and after every measured mix.

The query set
