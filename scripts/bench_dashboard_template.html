Overview Load Queries Memory Query set Raw data

One run of bench/run_bench.py — vortex-rdflib's VortexStore compared against rdflib's in-memory Memory store and oxrdflib (Oxigraph), executing a synthetic representative SPARQL set: single-pattern lookups and scans, anchored star and unanchored chain joins, and feature queries (FILTER, DISTINCT, ORDER BY + LIMIT, GROUP BY).

SPARQL evaluation is rdflib's engine for every store — the store serving triple patterns is the variable — with two deliberate exceptions kept as reference points: Vortex rows marked pushdown hand whole BGPs to vortex-rdflib's code-space evaluator, and the native SPARQL row delegates the query string to Oxigraph's own engine. The dataset's distinct-term count scales with rows (each subject described by ~10 triples, a small closed predicate vocabulary, IRI + typed/plain/lang literal objects), so term handling is actually exercised. Every query is non-empty by construction, and result counts are cross-checked across stores.

LOAD

N-Triples to queryable store

Cold start: parse/build from the shared .nt file until the store answers queries. Vortex rows include serialize_rdf (building the .vortex file) plus store open; rdflib and oxrdflib rows are Graph.parse. One sample — read magnitudes, not decimals.

QUERY

SPARQL execution, per query

Median wall-clock time to execute and fully consume each query. Green marks the fastest store in each column; the grey multiplier is the slowdown vs that column's best. Ruled-off rows change what is being measured: Vortex rows below the first rule run on rdflib's default BGP evaluator (no pushdown — the A/B for its effect), and the final row swaps in Oxigraph's native SPARQL engine.

MEMORY

Peak memory (RSS)

Each store's full lifecycle — parse/build, every query, result materialization — runs in its own process, so this is a clean per-store peak resident-set size: the kernel-tracked high-water mark (VmHWM), not a point-in-time sample. Store footprint is RSS after load minus the process baseline before it — what holding the dataset costs. Lower is better; smallest first.

SET

The query set

Anchor terms and thresholds are derived from the dataset generator's modular arithmetic, so every query matches at least one row by construction. heavy queries touch the whole dataset (or a whole predicate's bindings joined against the store) and run with a lower iteration budget.
